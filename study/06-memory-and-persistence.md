# 6. 메모리 소유권과 영속성

C로 자료구조를 만들 때는 값을 어디에 저장할지와 함께 **누가 언제 해제할지**를 정해야 합니다. 메모리가 올바르게 관리되는지와 서버가 꺼진 뒤 데이터를 복구할 수 있는지도 서로 다른 문제입니다.

## C를 선택한 이유와 비용

처음에는 C와 MSVC를 선택했고, 짧은 구현 기간을 고려해 TypeScript + Node.js도 비교했습니다. 이후 학습 인수인계에서 **C / Windows / MSVC**로 결정했습니다.

C는 메모리 배치와 문자열·노드의 수명을 직접 다루기 좋습니다. 대신 할당 실패, 범위 초과, 해제 후 접근과 같은 위험을 직접 관리해야 합니다. TypeScript를 쓰면 수동 메모리 관리 부담은 줄지만 해시 충돌, TTL, 요청 처리와 검증까지 사라지는 것은 아닙니다.

선택한 언어만으로 더 빠르거나 안전하다고 판단하지 않습니다. 구현의 정확성과 측정 조건으로 확인해야 합니다.

## 소유권을 먼저 정하는 이유

호출자가 문자열을 전달했을 때 저장소가 주소만 기억하는지, 복사본을 보관하는지에 따라 수명이 달라집니다. 호출자의 임시 버퍼가 사라져도 저장소가 그 주소를 쓰면 문제가 생깁니다.

| 작업 | 결정하거나 확인할 내용 |
| --- | --- |
| 새 키 저장 | 키·값·노드를 누가 할당하고 소유하는가? |
| 값 조회 | 복사본인지 빌린 주소인지, 언제까지 유효한가? |
| 덮어쓰기 | 새 값 준비 실패 시 기존 값은 유지되는가? |
| 삭제 | 연결을 고친 뒤 키·값·노드를 각각 해제하는가? |
| 리해싱 | 노드를 이동하는가, 새로 만드는가? 실패 시 되돌릴 수 있는가? |
| 종료 | 모든 버킷과 남은 노드를 정리하는가? |

저장 시 문자열을 복사해 소유하는 방식은 현재 제안이며 아직 함수 계약으로 확정하지 않았습니다. 빈 키 거부·빈 값 허용 역시 검토 질문으로만 제시됐습니다.

## 실패해도 기존 상태를 보존하기

덮어쓰기에서 이전 값을 먼저 해제한 뒤 새 메모리 할당에 실패하면 정상 데이터까지 잃을 수 있습니다. 새 자원을 먼저 준비하고 성공한 뒤 교체하는 방식 등을 검토해야 합니다. 구체적인 함수 반환값과 실패 정책은 첫 구현 전에 정합니다.

리해싱도 마찬가지입니다. 새 버킷 배열 할당에 실패했을 때 기존 항목이 여전히 조회 가능해야 한다는 기준을 고려하고, 실패를 주입할 방법과 통과 조건을 합의해야 합니다.

## 검사할 오류

- **누수:** 더 이상 필요 없는 할당을 해제하지 않아 메모리가 남는 상황
- **Use-after-free:** 이미 해제한 메모리를 다시 읽거나 쓰는 상황
- **Double free:** 같은 할당을 중복 해제하는 상황
- **범위 초과:** 확보한 배열·문자열 경계 밖을 접근하는 상황

도구가 오류를 보고하지 않았다는 사실만으로 모든 경로가 안전하다고 결론 내리지는 않습니다. 어떤 입력과 반복 경로를 실행했는지 함께 남깁니다. MSVC의 진단 도구와 AddressSanitizer 사용 가능 여부는 실제 설치 환경에서 확인해야 하며, 아직 검증하지 않았습니다.

## RAM과 종료 후 복구

메모리 저장소만 구현하면 프로세스 종료 후 저장한 값을 복구할 수 없습니다. 종료할 때 메모리를 올바르게 해제했다는 사실은 데이터가 디스크에 보존됐다는 뜻이 아닙니다.

실제 Redis에는 시점의 데이터를 보관하는 RDB 스냅샷과 변경 명령을 기록하는 AOF 같은 영속성 방식이 있습니다. 저장 주기와 디스크 반영 정책에 따라 비용과 장애 시 손실 범위가 달라집니다.

이번 Mini Redis에서 영속성은 선택 과제입니다. 우선 저장·조회·삭제, 만료, 외부 사용과 검증을 완성한 뒤 검토합니다. 현재는 재시작 복구나 무손실 보관을 보장하지 않습니다.
