# 7. Mini Redis의 설계 선택

이 문서는 일반적인 Redis 설명과 구분해 **우리 프로젝트에서 정한 내용**을 기록합니다. 2026년 11월 13일 인수인계 자료와 이후 대화의 정정 사항을 반영했습니다. 실제 구현 결과는 아직 없습니다.

## 구현 범위

문자열 키·값을 저장하는 해시 테이블 코어, 저장·조회·삭제와 TTL, HTTP 접근, 동시 요청 안정성, 외부 응답 캐싱 예제와 비교 측정이 중심입니다. Redis의 모든 자료형과 프로토콜 호환을 목표로 하지 않습니다.

팀의 두 사람 모두 Redis와 DBMS의 전 과정을 경험합니다. 이 저장소의 기록은 Redis에 집중하고, Redis 개념과 조건 정리를 마친 뒤 DBMS 학습·정의를 이어갑니다.

## 현재 선택과 특성

아래는 선택 목록을 읽는 입구입니다. [구조와 동작](../docs/DESIGN.md), [대안별 이득·비용과 미검증 근거](../docs/DECISIONS.md)를 함께 읽습니다. 일반적인 기술의 장점을 적었다고 이번 상황에서 최선임을 증명한 것은 아닙니다.

| 항목 | 선택 | 이유·주의점 |
| --- | --- | --- |
| 환경 | C, Windows 네이티브, MSVC | 메모리와 자료구조를 직접 다룸. 할당·해제 검증 필요 |
| 값의 범위 | 문자열 | 핵심 저장 동작에 집중. 인코딩·NUL·길이 제한은 미정 |
| 키 탐색 | 직접 만든 해시 테이블 | 개별 키 조회·수정·삭제를 빠르게 처리하는 구조 |
| 충돌 | 연결 리스트 체이닝 | 충돌과 첫·중간·끝 노드 삭제를 추적하기 쉬움 |
| 해시 | FNV-1a 64비트 | 구현과 검증이 단순한 비암호학적 함수 |
| 초기 버킷 | 16개 | 작은 초기 크기. 최적값으로 검증된 것은 아님 |
| 확장 | 신규 키로 적재율 0.75 초과 시 2배 | 평균 탐색 후보 증가를 제한. 13번째 신규 키에서 첫 확장 |
| 재배치 | 기본 리해싱 | 한 번에 재배치하는 구조 우선. 지연을 측정한 뒤 개선 검토 |
| 만료 | 수동적 + 능동적 | 오래된 값 반환 방지와 접근 없는 항목 회수를 함께 다룸 |
| 만료 검사 | 100ms, 최대 100개 키, 버킷 순차 진행 | 초기 검사 비용 제한. 커서와 빈 버킷 비용은 설계 필요 |
| 실행 | 같은 스레드의 이벤트 루프 | 저장소와 TTL 작업 사이의 노드 수명 충돌을 줄임 |
| 외부 인터페이스 | HTTP API | 외부 사용성과 저장 엔진 검증에 집중 |
| 일반 저장 | 덮어쓰기 시 기존 TTL 제거 | 새 값의 만료 여부를 명확히 함 |
| TTL 포함 저장 | 새 만료 시각 설정 | 재저장 시 이전 만료를 그대로 쓰지 않음 |
| 만료 경계 | 현재 시각 >= 만료 시각 | 정확한 경계부터 값을 반환하지 않음 |

16개, 0.75, 2배, 100ms, 100개는 **프로젝트의 초기 정책**입니다. 실제 Redis의 고정 수치라고 설명하지 않습니다. 적재율은 키 수/버킷 수이며, 덮어쓰기는 키 수를 늘리지 않습니다.

## 아직 정하지 않은 내용

- 저장 엔진 함수의 반환값, 키·값 소유권과 조회 결과의 수명
- 빈 키·빈 값, 최대 길이, 문자열 인코딩과 NUL 처리
- 할당 실패, 저장 공간 확장 한계, 오류 정책
- TTL 단위·시간원·범위와 오버플로 처리
- 삭제·삽입·리해싱 후에도 안전한 만료 검사 위치 표현
- HTTP 서버 라이브러리, 구체적인 버전 번호, 라우트·응답·오류 형식
- 요청 본문·동시 연결 제한, 타임아웃, 과부하 처리
- 실제 빌드 도구 구성, 메모리 검사 도구와 테스트 실행 명령
- 캐싱 데모의 데이터와 원본 API, 부하 규모와 성능 판정 기준

Libevent는 후보이고 Windows/MSVC 빌드가 확인된 선택이 아닙니다. HTTP/1.1은 인수인계의 추천안입니다. HTTP API 채택은 확정됐지만 버전 번호를 새로 단정하지 않습니다. API의 `PUT /keys/{key}`와 TTL 쿼리 표현은 제안 단계입니다.

## 선택 기능

영속성, HTTP/2 프록시, 문자열 외 자료형은 초기 필수 범위에 넣지 않습니다. 핵심 동작과 검증을 마친 뒤 필요성과 시간을 보고 검토합니다.

## 변경 이력

| 이전 | 현재 |
| --- | --- |
| 한 사람 Redis, 다른 사람 DBMS 담당 | 두 사람 모두 Redis와 DBMS 전 과정 경험 |
| C와 TypeScript를 비교하며 언어 재검토 | 최신 인수인계에서 C·MSVC로 결정 |
| 줄바꿈으로 구분하는 자체 TCP 명령 | HTTP API 채택, 옛 명령 프레이밍은 폐기 |
| README에 날짜별 일정·학습 목표 기재 | 사용자를 위한 개요와 학습 문서 입구로 정리 |
| 팀 저장소에 학습 브랜치 검토 | 개인 포크의 study-jye에서 정리 |

학습 기록을 작성했다고 구현·테스트를 마친 것은 아닙니다. 다음 구현 단계에서는 이 결정에 필요한 함수 계약과 필수 테스트의 기대 결과를 함께 정합니다.
