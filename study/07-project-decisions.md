# 7. 프로젝트의 현재 선택

제품 계약은 [요구사항](../docs/REQUIREMENTS.md), 구조는 [설계](../docs/DESIGN.md), 이유·대안은 [선택 기록](../docs/DECISIONS.md), 외부 규격은 [API](../docs/API.md)가 기준이다. 이 문서는 읽는 입구이며 계약을 따로 재정의하지 않는다.

| 항목 | 현재 선택 |
| --- | --- |
| 언어·HTTP·서버 | Python + Flask + Waitress, Windows |
| 자료구조 | 직접 만든 해시 테이블, FNV-1a 64비트, 연결 리스트 체이닝 |
| 확장 | 초기 16, 신규 키로 0.75 초과 시 2배 전체 리해싱 |
| 동시 접근 | 1프로세스, 요청 4스레드와 청소 1스레드, 저장소·락 하나 |
| 입력 | 문자열, 빈 키·값 허용, 원문 유지, UTF-8 키 1 KiB·값 1 MiB |
| TTL | 양의 정수 밀리초, 단조 시간, 생략은 무기한, 일반 덮어쓰기는 TTL 제거 |
| 청소 | 목표 100ms, 최대 100키·100버킷, 커서 유지·삭제 보정·확장 시 초기화 |
| HTTP | JSON 본문, POST /set·/get·/delete, 127.0.0.1:8080, 본문 8 MiB |
| 영속성 | 초기 범위 제외 |

위 수치는 합의한 시작값이다. 성능 최적값 또는 실제 Redis의 고정값으로 설명하지 않는다. 문서의 존재는 구현이나 숙련의 증거가 아니다. 남은 극단 입력·용량·실패 경계는 [요구사항의 미정 항목](../docs/REQUIREMENTS.md)에 표시한다.

## 변경 이력

| 이전 | 현재와 이유 |
| --- | --- |
| C·MSVC | Python. 수동 메모리 관리보다 저장소 흐름과 검증에 집중 |
| 같은 이벤트 루프의 요청·청소 | Waitress 요청 스레드 + 청소 스레드, 같은 저장소 락으로 보호 |
| 자체 TCP 줄바꿈 명령 | 외부 사용성을 위한 HTTP API |
| Libevent·PUT /keys/{key} 검토 | Flask·Waitress와 JSON 명령 API 확정 |
| 각자 Redis/DBMS 분담 | 두 사람 모두 두 프로젝트 전 과정 경험 |
| 팀 학습 브랜치 검토 | 개인 포크 study-jye에서 학습·설계 기록 |

첫 구현 단위의 저장·조회·삭제·충돌 테스트는 합의했지만 아직 실행하지 않았다. 현재 상태와 다음 작업은 [WORKLOG](../WORKLOG.md)를 읽는다. GitHub 반영 여부도 로컬 문서 존재와 구분한다.
