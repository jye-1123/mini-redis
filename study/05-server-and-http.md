# 5. 서버와 동시 요청, HTTP API

저장 엔진이 메모리에 값을 보관하더라도 다른 프로그램이 사용하려면 요청을 받는 입구가 필요합니다. 우리 프로젝트는 이 입구를 HTTP API로 제공하기로 했습니다.

## 전체 요청 흐름

```text
외부 앱
  → HTTP 요청
  → 서버 라이브러리의 HTTP 처리
  → 경로·본문·입력값 검사
  → 저장 엔진의 저장/조회/삭제
  → HTTP 응답
```

HTTP 처리는 요청을 해석하고 응답으로 바꾸는 역할을 맡고, 저장 엔진은 해시 테이블과 값의 수명을 관리합니다. 둘의 경계를 나누면 HTTP를 연결하기 전에도 저장소를 단위 테스트할 수 있습니다.

## TCP와 HTTP의 관계

TCP는 순서 있는 바이트 흐름을 전달하고, HTTP는 요청의 메서드·경로·헤더·본문과 응답의 의미를 정합니다. HTTP/1.1은 보통 TCP 위에서 사용되므로 두 기술은 같은 층의 대체재가 아닙니다.

초기에는 `SET key value`를 줄바꿈으로 나누는 자체 TCP 규칙을 검토했습니다. 외부 사용성과 저장 엔진 검증에 집중하기 위해 **HTTP API로 변경**했습니다. 예전 줄바꿈 명령 문법은 현재 외부 규격이 아닙니다.

실제 Redis 클라이언트는 RESP를 사용합니다. 우리 HTTP API를 만들었다고 `redis-cli`와 호환되는 것은 아닙니다. `SET/GET/DEL`은 저장 동작을 설명하는 이름이며 HTTP 요청 명세와 구분합니다.

## 아직 확정하지 않은 API 예시

아래는 전달받은 제안입니다. 구현된 경로나 승인된 규격이 아닙니다.

| 목적 | 요청 제안 | 응답 제안 |
| --- | --- | --- |
| 저장 | `PUT /keys/{key}` + 본문 | 성공 상태 |
| TTL 포함 저장 | `PUT /keys/{key}?ttl=60` | 성공 상태 |
| 조회 | `GET /keys/{key}` | 값 또는 없음 |
| 삭제 | `DELETE /keys/{key}` | 삭제 결과 |

키의 URL 인코딩, TTL 단위, Content-Type, 오류 형식, 없는 키의 삭제 결과와 상태 코드를 함께 정해야 합니다. HTTP 본문에는 공백과 줄바꿈이 들어갈 수 있으므로 옛 줄바꿈 프로토콜의 제한을 그대로 옮기지 않습니다. NUL을 포함한 값의 지원 여부는 저장 엔진의 표현 방식과 연결됩니다.

HTTP API 사용은 확정됐습니다. HTTP/1.1은 인수인계 자료의 추천안이며, 이 학습 기록에서 특정 버전 번호를 확정으로 추가하지 않습니다. HTTP/2나 앞단 프록시가 해시 탐색과 긴 리해싱을 자동으로 빠르게 만들지는 않습니다.

## 단일 스레드 이벤트 루프

연결에 읽을 데이터가 생기거나 타이머 시간이 되면 콜백을 실행하는 구조를 사용합니다. 저장 엔진과 TTL 작업은 같은 스레드에서 순서대로 처리하도록 설계합니다.

```text
이벤트 대기 → 요청 A 처리 → 만료 검사 → 요청 B 처리 → 이벤트 대기
```

외부 클라이언트가 동시에 연결할 수 있어도 저장소 변경 콜백은 순차 실행됩니다. 같은 노드를 읽는 동안 다른 저장소 스레드가 해제하는 문제를 줄이려는 선택입니다. 네트워크 연결마다 스레드를 만들지 않아도 되는 장점도 있습니다.

이는 우리 Mini Redis의 구조입니다. 실제 Redis의 모든 버전·모듈·I/O가 단일 스레드라고 일반화하지 않습니다.

## 순차 처리로도 남는 문제

읽기와 쓰기가 각각 별도 요청이면 두 요청 사이에 다른 클라이언트의 요청이 들어올 수 있습니다. 예를 들어 두 앱이 모두 0을 읽고 1을 저장하면 최종 값은 1이 될 수 있습니다. 테이블 손상이 없다는 것과 여러 요청으로 된 작업의 원자성이 보장된다는 것은 다릅니다. 이번 필수 범위에 트랜잭션이나 증가 명령이 포함됐다고 가정하지 않습니다.

또한 콜백 하나가 오래 걸리면 다른 요청도 기다립니다. 대량 리해싱, 긴 만료 검사, 큰 본문 처리, 동기식 디스크·외부 API 호출은 지연을 늘릴 수 있습니다. 캐싱 데모의 원본 조회는 외부 데모 앱에서 수행하는 구조를 검토하며, 저장 서버가 외부 조회를 기다리도록 임의로 확장하지 않습니다.

## 라이브러리를 고르기 전에 확인할 일

Libevent는 이벤트·타이머·HTTP 기능을 제공하는 후보입니다. 아직 설치하거나 Windows/MSVC 빌드를 확인하지 않았습니다. Mongoose도 학습 중 후보로 언급됐지만 채택하지 않았고 라이선스 검토도 남아 있습니다.

선정 시에는 실제 빌드, 라이선스, HTTP와 타이머 통합, 본문·연결 제한, 콜백 스레드를 확인해야 합니다. 저장 엔진 콜백을 여러 워커에서 실행하면 단일 스레드 소유 가정이 깨집니다.

## 검증할 질문

- 느린 클라이언트 하나가 전체 요청 처리를 막지 않는가?
- 연결이 끊겨도 요청 객체와 메모리가 정리되는가?
- 리해싱이나 만료 회수 중 다른 조회의 지연은 얼마인가?
- 여러 요청이 겹쳤을 때 어떤 순서와 결과를 보장하는가?
