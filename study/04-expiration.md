# 4. 값은 언제 만료되고 언제 지워지는가

TTL(Time To Live)은 값을 유효하게 사용할 수 있는 기간입니다. **더 이상 값을 반환하면 안 되는 시각**과 **그 값의 메모리를 실제로 회수하는 시각**을 구분해야 합니다.

## 논리적 만료와 물리적 삭제

어떤 값의 만료 시각이 10:00:05라고 가정합니다. 10:00:05 이후에는 해당 값을 조회해도 반환하지 않아야 합니다. 아직 메모리에 노드가 남아 있더라도 유효한 값은 아닙니다.

우리 프로젝트의 경계 규칙은 다음과 같습니다.

```text
현재 시각 < 만료 시각  → 유효
현재 시각 >= 만료 시각 → 만료
```

시간 단위와 시간원은 아직 미정입니다. 시스템 시각 변경에 어떻게 대응할지, TTL 범위를 넘는 덧셈을 어떻게 막을지도 정해야 합니다.

## 수동적 만료

조회 등으로 키에 접근할 때 만료 여부를 확인하고, 만료했다면 삭제한 뒤 없는 키로 처리합니다. 주기적인 청소가 늦어도 오래된 값을 반환하지 않게 만드는 경로입니다.

이 방식만 있으면 다시 조회되지 않는 만료 항목이 메모리에 오래 남을 수 있습니다.

## 능동적 만료

주기적으로 일부 키를 검사해, 접근이 없는 만료 항목도 삭제합니다. 한 번에 전체 테이블을 훑으면 요청 처리가 지연될 수 있어 검사량을 제한합니다.

| 항목 | Mini Redis의 초기 정책 |
| --- | --- |
| 실행 간격 | 100ms |
| 검사량 | 한 번에 최대 100개 키 |
| 탐색 | 버킷을 순서대로 검사하고 다음 위치 유지 |
| 실행 스레드 | 요청을 처리하는 이벤트 루프와 동일 |

이 수치는 초기 설정이며 실측 결과가 아닙니다. 모든 만료 키가 100ms 안에 삭제된다는 보장은 없습니다. 이벤트 루프가 다른 작업으로 바쁘면 타이머 콜백 자체도 늦어질 수 있습니다.

## 값을 덮어쓸 때의 TTL

| 동작 | 합의된 정책 |
| --- | --- |
| TTL 없는 일반 저장 | 새 값을 저장하고 기존 TTL 제거 |
| TTL 포함 저장 | 새 값을 저장하고 만료 시각 재설정 |
| 유효기간 없는 키 조회 | 시간에 의한 만료 없음 |
| 만료된 키 재저장 | 새 값과 새 정책으로 사용 |

이 표는 저장 엔진의 의미입니다. 외부 HTTP API에서 TTL을 경로나 본문 중 어디에 담을지는 아직 확정하지 않았습니다.

## 검사 위치를 유지하는 어려움

만료 검사 사이에 삭제나 리해싱이 발생하면 이전에 기억한 노드 주소가 더 이상 유효하지 않을 수 있습니다. 따라서 다음 검사 위치를 어떤 정보로 표현할지와 구조 변경 후 어떻게 보정할지 정해야 합니다.

키 100개라는 한도만으로 실행 시간이 제한되는 것도 아닙니다. 비어 있는 버킷을 오래 순회하거나 긴 체인을 반복 탐색할 수도 있습니다. **키 검사량과 버킷 순회 비용을 함께 고려한 진행 규칙**이 필요하며, 정확한 방법은 미정입니다.

## 무효화와의 차이

만료는 시간이 지났다는 이유로 값을 사용할 수 없게 하는 것이고, 무효화는 원본 변경 등으로 기존 값을 더 이상 사용하지 않겠다는 판단입니다. 예를 들어 가격 변경 직후 캐시를 삭제하면 TTL이 남아 있어도 다음 요청은 새 원본을 가져오게 할 수 있습니다.

삭제와 원본 조회가 겹치는 상황까지 정합성을 보장하려면 앱의 갱신 순서와 실패 처리도 검토해야 합니다.

## 검증할 경계

- 만료 직전·정확한 만료 시각·만료 직후 조회
- 일반 저장으로 덮어쓸 때 이전 TTL 제거
- 조회가 없는 만료 키의 최종 회수
- 삭제·리해싱 후에도 만료 검사가 계속 진행되는지
- 0, 음수, 너무 큰 TTL을 받았을 때의 정책
